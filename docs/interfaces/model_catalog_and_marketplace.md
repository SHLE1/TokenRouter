# 模型目录与市场

本文描述可请求的模型目录如何根据分组、价格配置和提供商能力解析出来，又如何整理成公开模型市场上的品牌、价格、容量和可用性。供应商完整的动态模型清单会变化，本文不列出；最终的用量结算事务见[路由与结算](../domains/routing_and_billing.md)。

<a id="model_catalog_resolution"></a>
## 目录解析

公开市场的分组筛选、每个请求的提供商预取和排序、辅助的容量和可用性、动态设置和输出组合，由 `routing.Marketplace` 执行；模型和公开统计的 HTTP 由 `routing/httpapi` 直接提供。app 绑定分组存储、settings.Store、billing 报价和 Dashboard 统计读取（各只有一个）；平台默认目录和显示名由 `routing/provider` 提供，app 直接注入选项，动态目录在调用时读取。市场展示、价卡和元数据的测试直接验证 `routing.Marketplace`；网关目录和实际查价的一致性测试，也直接组合市场的接口，不会另外构造一份市场服务。

`routing.RequestableResolver` 负责合并可请求的候选、分组白名单、"请求模型 → 分组映射模型 → 上游模型"，以及价格歧义的判断。`routing.RequestableCatalogue` 组合候选读取和模型列表的短缓存，由 app 直接绑定 provider 存储。`gateway/provider.ModelPolicy` 为目录和实际转发提供同一套平台模型判断，提供商记录和本次 attempt 的模型链分开传入。提供商的模型范围和一跳匹配由 provider 提供，平台专有的资格、thinking 和模型限流的观测、动态默认目录，通过小接口接入。

`routing.ModelList` 由 app 按 TTL 构造一次，按分组和入口的强制平台条件区分目录，nil 结果也会缓存，全进程共用一组指标，由应用时间轮按固定频率清理。请求模型和公开模型使用同一个可请求解析：从当前分组可调度的提供商能力生成候选，再执行 Key、分组和提供商的模型映射和范围校验。已有分组的目录来自组内提供商实际的模型和协议能力；解析结果为空时就是空，不会回退到一个假设的平台默认列表。创建分组时，管理端的候选可以汇总各平台的默认目录作为编辑参考，这些建议并不代表已经可以请求。

网关的四类模型目录 HTTP，由 app 直接构造 `gateway/httpapi.ModelsHandler`，复用同一个 `routing.RequestableCatalogue`。平台的展示数据由 `gateway/provider.ModelDisplayCatalogue` 提供；`gateway/modeldisplay` 只保存展示值、稳定合并和默认列表的规则。HTTP 负责 Key 别名、自定义列表和各协议的响应格式。Gemini 原生的列表和单模型查询，只保留支持 `gemini_generate_content` 的可请求模型，并使用本地的 Gemini 元数据；结果为空时，不会用某个上游或静态的默认列表补全。单模型查询需要先通过同一个目录的验证，未知或不在当前权限范围内的模型返回 404。复合 Key 逐个检查绑定的分组权限和协议，再加上前缀；强制 Antigravity 的路径只过滤提供商平台，分组的协议和模型限制照常生效。

提供商映射由 `provider.ResolveModelMapping` 解析，默认范围由 `provider/provider.DefaultProviderModels` 按提供商的平台、认证类型和特定资格提供。白名单缺失或为空时使用默认目录；手动配置的映射可以加入自定义的请求名，非空的白名单限定最终的模型。末尾通配符和 `*` 只参与匹配，不会作为模型 ID 返回。透传开关也要经过这层检查。返回的映射是独立的值；读取时不修改提供商内部派生的缓存，调度和展示的并发读取、调用方对结果的修改，都不会影响之后的请求。精确和通配的匹配复用 `routing/modelmap`；Qoder 专有的资格和默认目录由平台规则适配器提供，请求在执行时才改写。分组模型的拒绝提示由 routing 汇总候选，gateway/provider 提供站点的默认目录：只在候选合格、并且没有手动配置模型时才读取默认目录；手动配置过滤后为空时，返回非 nil 的空集合。

管理端提供商测试用的模型目录，由 `routing.AdminCatalog` 组合手动指定的平台、提供商的认证形态和按需解析的请求模型；默认目录通过 app 注入的 `routing/provider.AdminCatalogOptions`，在调用时读取平台快照。OpenAI 透传仍然使用明确的模型范围；Gemini Google One 和 OAuth、Antigravity、Qoder 站点和 Spark 影子提供商，各有自己的能力范围，Grok 的动态目录按需读取。HTTP 对 OpenAI、Grok 和 Claude/Gemini 类的模型，分别保持零值字段、省略字段和空数组或 null 的格式；管理测试的目录不代表提供商实际能执行的能力。

分组编辑页的模型列表候选和探测模型的选项，复用 `RequestableResolver`，按已保存的分组映射、白名单检查阶段、协议和提供商能力，返回请求模型名。自定义列表只在可请求的候选里筛选，并保持排序；历史上保存的上游模型名，不会重新出现在探针选项里。没有保存的分组策略修改，需要保存后重新加载候选。

用户可见的分组目录提供 `models: string[]` 和 `model_protocols: Record<string, ProtocolID[]>`，后者列出每个模型当前可以请求的客户端入口。两者只用于控制台的展示和配置生成，请求时仍要做权限和资格校验。Key 列表里内嵌的分组没有带目录时，前端按分组 ID 复用可见分组列表，不会逐行猜测默认模型。

Claude Code、Codex、Gemini、Grok、OpenCode 和 CC Switch 的配置，按用户选择的客户端协议和实际的模型生成。有 `model_protocols` 时按它过滤；目录为空时不生成虚构的示例。Key 级的映射（精确匹配或最长的末尾通配符）按一跳的目标整理出可用的模型和协议，复合 Key 的示例加回已绑定的前缀；导出不会因为品牌或模型名而加上 `/antigravity` 等强制平台的路径。tf CLI 回环协议保持原格式。

模型 ID 是客户端的请求键，display name 是展示信息，pricing model 是解析价格用的键，三者可以不同。Key 级重定向和分组映射要让 `/v1/models`、`/models`、实际调度和响应模型恢复保持一致；目标无法请求的别名，不应该只出现在列表里。

## 市场可见性

公开市场只返回处于 active、非 exclusive、并且至少有一个 active 提供商的分组；解析后没有可请求模型的分组也会被隐藏。排序使用分组手动设置的顺序；市场不会按临时价格或实时错误重新排列。

展示品牌优先使用 `display_brand`，为空时使用分组名。公开的分组数据包括描述、品牌、倍率和模型数，不包含单一的上游平台。模型仍然可以带自己的厂商和能力信息，展示品牌和执行的提供商平台无关。

模型级的数据附带 `attributes`，包括有效的显示名、长度、模态和能力信息；`input_modalities` 和 `output_modalities` 保留为兼容字段。新的属性数据里，未知的字段不会根据价格或名称猜测；只有旧接口没有返回 `attributes` 时，前端才使用历史的模态推断。属性读取失败不影响价格展示。

## 目录元数据查询

`modelcatalog` 解析 models.dev 的统一目录，负责供应商身份索引、属性和内容版本。`modelcatalog/provider.Service` 在应用生命周期内下载、缓存，并原子发布统一目录和它的价格数据；`billing/pricing` 把目录报价归一化为 `CatalogModelPricing` 计费模型，并解释本地补充和计费规则。app 的目录装配只创建一个运行实例，计费和属性的使用方共用它。目录维护的步骤封装在运行时里，对外提供生命周期、查询、快照和强制更新。价格和属性一起更新；候选目录失败时，保留整个旧版本。代理失败的策略和 URL 校验，由现有的出站规则执行。

生产环境只使用 models.dev 的加载流程，远程入口是 `https://models.dev/catalog.json`，按 `pricing.check_interval_minutes` 检查（默认每 10 分钟），使用 ETag 条件请求和本地的内容摘要；管理员可以强制更新。程序内嵌了一份经过解析验证的压缩离线快照和官方价格补充，并附上 models.dev 的 MIT 许可。官方补充随二进制一起升级和回退，不依赖外部的资源目录。首次启动和网络故障时，可以使用磁盘上或内嵌的离线目录；缓存文件是 `models_dev_catalog.json`，完整解析成功后，通过临时文件替换。管理员接口返回版本、最近一次成功更新的时间和最近一次更新的错误。本地文件在合并之前，把旧的 `litellm_provider` 归一化为 `provider`，同时有新字段时（包括空值和 `null`）以新字段为准；内部的来源分类是 `catalog`，不会覆盖实际的数据出处。远程返回 304 时，本地层照常校验。

裸模型名优先选择原厂的记录。明确的 `canonical_model_id` 归属优先；没有这个关联时，已知的原厂端点（包括 OpenAI、Anthropic、Google、xAI、Mistral 等）仍然可以被识别为原厂，不要求每个模型都出现在公共资料表里。原厂端点托管的其他作者的模型，继续按明确的 canonical 归属识别。Azure、OpenRouter 等独立的供应商，不会通过这条规则获得原厂身份；其他来源无法确定时，保留歧义，不会按遍历顺序挑一个价格。供应商限定的名称先精确匹配，已知的供应商前缀不会在查询时被删掉，从而借用其他来源的数据。只有模型公共资料的记录也能参与属性查询，不要求有价格。

公开市场通过 `billing.PriceResolver.PublicQuote`，使用和实际扣费一致的价卡解析。价格和属性按完整的模型 ID 查询，只清理大小写、首尾空白和已知的 Google 资源路径；供应商限定的名称保持来源隔离。Claude 的点号和短横线、日期版本和档位后缀，都代表不同的身份，不互换，也不补全。完整的目录条目各自生效，价格、缓存、上下文阶梯和能力字段不会从基础条目拼接过来。

价格配置的价卡先按原始的请求名匹配精确和通配规则，再查询同一型号的协议资源路径候选。完整型号手动配置的价卡和零价都保留，价格查询不按分组或提供商平台隔离。完整型号没有价格时返回未定价，不会剥离日期、effort 后缀或供应商名称去借用其他价格。

Gemini、OpenAI、Claude 和 Grok 的模型后缀按完整 ID 处理，不生成基础型号的候选或 effort。上游实际提供的 `high`、`low`、`medium`、`tiered`、`max`、`thinking` 等完整型号，仍然可以配置独立的价格和属性。Grok 运行时的默认文本模型，只用于允许省略模型的请求，不参与目录的别名查询。

GPT-5.6 系列的内置目录、白名单和配置导出，只提供 `gpt-5.6-sol/terra/luna`，不注册裸的 `gpt-5.6`，也不会把裸名称自动重定向到 Sol 或旧的 GPT。外部目录或管理员手动配置的条目，照常遵守通用的查表规则；裸名称没有手动定价时，不借用 Sol 或默认 GPT 的价格。

展示属性读取 models.dev 的 `modalities.input/output`，支持文字、图片、音频、视频和 PDF。字段缺失和零长度表示未知或不适用；明确的 false 和空的模态数组会保留。本地旧价格 JSON 里的模态推断，只用于兼容价格的使用方，分组的有效属性使用独立的解析器。

裸模型名因为有多个供应商的记录而产生歧义时，属性查询在精确查询失败之后，检查这些记录的 `canonical_model_id`。所有记录都明确指向同一个公共模型、并且公共资料存在时，使用这个公共模型的属性；归属缺失、不一致或者公共资料缺失时，保持未知。供应商限定的名称不使用这条回退，已经有精确条目的也不会用公共资料补字段。属性的回退不影响价格索引和价格歧义的状态，不会借用任何中继的报价。

目录和手动配置都没有命中时，返回缺价，不再查询 Go 里的静态价格表；也不会使用日期、系列、Spark 跨型号重定向或默认型号去猜价格。离线启动使用同一份 models.dev 快照，网络失败时保留最近一次有效的目录。价格规则不作为能力查询的继承依据，也不改写公开的模型 ID 或上游的请求 ID。

models.dev 的目录、属性和本地补充在同一个版本里发布，只读快照使用同样的完整身份规则。原厂的裸名和明确的供应商记录，按来源索引查询；手动填写的零价和本地新增的条目保持有效；未知型号不会按目录的遍历顺序选价格。

## 目录价格换算

目录报价以美元每百万 token 提供，内部换算为美元每 token。`cost.tiers` 里明确的上下文阈值，优先于兼容的 `context_over_200k`；多个阶梯各自保留绝对的输入、输出和缓存价，按 `(min,max]` 的区间展示和结算。价格配置手动设置的区间继续优先；关闭内置长上下文规则时，不应用目录的阶梯。Fast 报价保留明确的零价，展示和结算使用同一份换算结果。

xAI 达到上下文阈值就切换价格。转换层把这类目录阶梯的内部分界点减一，例如原始阈值 200,000 对应基础档的最大值 199,999；结算、模型广场和管理员默认价格页，使用转换后的区间。原始的目录阈值保持不变，其他供应商仍然要超过阈值才切换档位。

价格配置的图片输入、图片输出单价，覆盖每个目录阶梯；手动填写的零值和没填写的含义，在各档保持一致，覆盖和缩放只修改请求用的价格副本。图片输入没填或为零时，按所在档的文本输入价计费；图片输出没填或为零时，不收图片 token 的费用。

默认目录的图片输出价，也会保留"是否明确给出"这个信息：目录或本地补充给出零价时，按免费结算；只有这个价格桶缺失时，才回退到文本输出价。

原厂 Google 的 Gemini 生图记录里，`cost.output` 表示图片输出 token 的费率，换算为 `output_cost_per_image_token`；文本和思考的输出价，由媒体补充文件填入，来源标为 `local_supplement`。目录里已有的图片费率，优先于补充文件；管理员可以通过关联的价格配置，设置用户侧的这两项单价。这种解释只用于原厂 Gemini 生图记录，Deep Research 和中继报价不适用。models.dev 缺少完整的文本输入、输出价时，token 保持未定价，独立的媒体价格仍然可以查询；明确的零价不算缺失。价格依据见 [Google 官方定价](https://ai.google.dev/gemini-api/docs/pricing)。

`source` 和 `price_sources` 区分 models.dev、本地补充和规则补充。补充只填缺失的字段，目录里明确的零价同样优先；自定义补充优先于内嵌补充，媒体尺寸表等复合字段整体选择一个来源，不会因为条目同名而覆盖目录的现价。补充按"提供方加原始模型 ID"，同步到同一个原厂记录的裸名和限定名：先应用精确的键，再填补其他等价名称的空缺；日期版本和中继记录不共享补充。

官方补充的维护源是 `backend/internal/modelcatalog/model_pricing_supplements.json`，通过 `go:embed` 编进二进制；`pricing.fallback_file` 默认为空，只读取手动配置的自定义补充。自定义文件删除后，恢复内嵌的值；文件损坏时，保留上一次有效的目录。官方补充只保留目录没覆盖、当前计费需要、并且能够核实来源的字段，并记录 `source_url` 和 `verified_at`。展示属性来自 models.dev 和分组属性配置；补充文件里旧的属性字段，不会成为新的展示属性来源。型号专属的 Fast/Flex、Max、缓存写入和峰谷数值，不写在 Go 代码里；需要时，通过 `fast_multiplier`、`flex_multiplier`、`max_reasoning_effort_multiplier`、`cache_write_multiplier`、`cache_write_1h_multiplier` 和 `time_pricing` 明确声明。没有规则时，不会根据型号生成加价或折扣。Fast 的缓存写入价格，对所有来源按同一规则缩放 5m 和 1h 两种 TTL 的费用，来源标签和收费无关。

`image_prices` 按 1K、2K、4K 保存美元每张，`video_prices` 按 480p、720p、1080p 保存美元每秒；缺失的维度保持缺价，不套用通用的尺寸倍率。旧的 `output_cost_per_image` 仍然表示不分尺寸的单张价格。操作价格在保留节点 `_billing_defaults` 里，自定义的值按字段叠加到内嵌的默认值上，保留明确的零价，不会进入模型列表；它们和价格、属性一起校验、发布和复制。历史账单和任务的资金快照不会重算。

统一目录发布时，检查价格解析的逐条诊断。模型的价格字段类型错误，或者嵌套的阶梯解码失败时，这一轮更新返回带模型名和字段信息的错误，原有的价格、属性、版本、更新时间和磁盘缓存都保留，只更新错误状态。只有属性、没有报价的模型，是合法的目录记录，属性查询照常可用。

目录发布保留逐条的解析诊断：未知模型上没有价格的补充，不生成计价条目；非法字段或非对象的条目，会让这一轮更新被拒绝。孤立的缓存阶梯和只有单侧的阶梯会输出诊断；已发布模型的倍率阶梯或绝对阶梯在更新后消失时，输出告警，便于确认是不是有意的调整。

## 价格展示

模型展示的价格和实际结算使用同一个计费解析器：先取价格配置的有效价格，没有时取统一模型目录的价格，作为基础价格，再应用分组倍率。分组映射已经给出 pricing model 时，展示层不再猜测别名链。只配置了服务层级、Max 推理或分时倍率的条目，继承价格配置或目录的基础价，并按字段覆盖同名的倍率。管理员配置的积分人民币单价和美元汇率都有效时，才展示相对官方价的比例和人民币等价；任何一个缺失或非法时，省略这部分。分组展示和模型计价都不依赖"单一平台"这样的假设。

`context_intervals` 就是用户实际的定价。价格配置设置了有效的 token 区间时，按共同的 `(min, max]` 区间展示和结算，并优先于模型内置的长上下文规则；价格配置关闭 `long_context_pricing_enabled`，也不会把这类手动设置的区间压平。没有有效的手动区间、而模型带有长上下文元数据时，开关开启会合成基础档和长上下文档两档，关闭时展示并结算单一的基础价。模型目录的 `input/output_cost_per_token_above_*k_tokens`，在解析层换算为同一组阈值和倍率；手动写的 `long_context_*` 字段（包括 `0`）优先，解析时会清除这个条目 models.dev 默认的绝对阶梯，改用手动的阈值和倍率，所以阈值 `0` 可以关闭默认的长上下文加价。用 `null` 删除覆盖字段后，恢复目录的默认规则。

用户售价由分组关联的价格配置覆盖目录，手动填写的零价优先。图片模式的报价、普通图片的结算、创作台和批量图片的预占，都使用逐尺寸查价：配置过的尺寸用价卡，没配置的尺寸查目录。按次模式只使用自己的标签、上下文区间和默认价，不借用目录的图片价；没配置尺寸、也没有明确的默认价时，报价里省略这个尺寸，任务的单价查询和普通结算返回缺价。按次价卡带有上下文区间时，实际请求仍按已知的总输入量匹配；报价和固定的单张预占没有上下文数据，只有命中明确的标签，或者所有上下文价都和明确的默认价一致时，才能给出固定价格。手动填写的零价不受影响。系统没有全局的默认价卡，也不读取 `pricing.override_file`。

合成长上下文档时，普通档和 priority/Fast 档的缓存创建、缓存读取价格，都按输入侧的倍率调整；缓存创建的标准、5 分钟和 1 小时三种价格，使用相同的倍率规则。展示会补齐手动区间之前、之后和中间有基础价的范围；缺价的范围不会显示成零价，也不会被其他区间的价格代替。只有所有正的上下文范围都有价格、并且普通价和 Fast 价一致时，才压平为单一价格。

返回的零价区间仍然保留范围标签和切换入口；JSON 里省略了零金额字段，不代表这个区间缺价。区间价格已经应用了分组倍率。计费模型、价卡、服务层级、最终 effort、用量、时刻和资金倍率都相同时，实际提供商的平台不会成为另一个售价维度。以上游模型作为计费来源时，先按提供商映射确定计费模型；不同路线无法给出一致的报价时，标记为歧义，不会猜一个统一的低价。

关联的价格配置开启了 `free_openai_fast` 的分组，模型广场上 Fast 的用户价格，和同一个 Standard 基础价、上下文档一致；判断是否展示 Fast 时，同时检查默认价和有效的区间，只有区间单价的自定义模型同样适用。只调整展示用的副本，结算的 Fast `total_cost` 和提供商统计不会因此改成 Standard。分时倍率按价格配置现有的展示方式处理，市场价格不做实时刷新。

共享价格配置和提供商统计 API 的 `cache_write_1h_price` 是可选字段，`cache_write_price` 代表 5m 档。1h 字段存在时，模型广场和结算按用量里 5m 和 1h 的明细分别计价，公开 DTO 下发两个单价；字段缺失时，按历史的单一价格处理。

公开的图片报价，单独检查完整型号的按张价格，token 价格缺失不会把有效的图片单价藏起来。报价、预扣费和实际结算都保留手动填写的零价；HTTP 的 `image_price_1k/2k/4k` 对有价格的尺寸返回数值（包括零），对缺价的尺寸省略字段，模型市场只展示已知的尺寸。没有对应型号和计价维度的目录报价时，返回缺价，不使用通用的按张单价，也不会把图片单价当成视频的每秒价格。固定的按张预留不接受 token 单价；上游生图响应报告了 token 用量、并且同一个完整型号有独立的 token 报价时，结算可以按实际的 token 计费。

未知或有歧义的价格，使用 `unpriced` 或 unknown 状态，不会填 0；价格指针明确为 0 才表示免费。Qoder 的公开别名和路由键，也按完整身份查询统一目录，有明确的价格就可以使用；具体的优先级见 [Qoder 原生上游](qoder_upstream.md)。

<a id="gateway_default_pricing"></a>
## 管理员默认价格查询

「模型管理」包括「价格管理」和「属性管理」。价格管理保持原来的 URL，有「价格配置」和「网关默认价格」两个页签。默认价格通过 `/api/v1/admin/pricing/defaults` 查询，支持按模型名、平台、计费模式筛选和分页；`/model` 和 `/models` 分别按模型提供自动填价和统一的模型名查询，不需要上游平台参数。默认目录列表里的平台标签，用于识别模型的来源，不是自定义价卡的查价维度。所有接口都需要管理员认证。「网关默认价格」只读，日常改价在「价格配置」里完成，一份配置可以关联多个分组。没有关联价格配置的分组，使用目录的默认价；提供商成本规则和用户售价相互独立。

工具栏的搜索框和筛选图标按钮放在左侧，平台和计费模式收在筛选面板里；右侧的刷新图标只重新查询列表。蓝色的「更新目录」按钮通过 `POST /api/v1/admin/pricing/defaults/update`，调用同一个价格服务的强制更新：配置了远程来源时，重新下载目录并加载本地补充；没有配置远程来源时，重新加载本地目录和补充层。更新成功后，保留当前的筛选并重新查询；更新失败时，显示错误，列表保持不变。请求期间按钮禁用，防止重复提交。

离线的手动更新和后台的本地重载，使用同一个流程。缓存文件读不了时，优先使用已经加载的内存目录，所以缓存目录只读，不影响本地补充文件生效；候选的价格仍然要完整校验，失败时保留已发布的版本和错误状态。这个流程自己持有更新锁，调用方不需要再加锁。

列表从当前加载的目录取一份独立的快照，用同一个 Calculator 的目录规则计算基础价格；本地补充已经包含在目录里。查询不会触发网络同步，也不叠加分组、用户或订阅的倍率。价格详情标明 token、图片、视频和倍率的单位，并附带缓存、服务层级和长上下文的规则。明确的零价和未定价分开显示。批量图片和创作台保存的资金和单价快照，不会因为查询或目录更新而重新计算。

输出模态不决定计费模式。默认价格页只在目录有明确的按张价格、或者命中了模型专用的媒体规则时，才展示按张或按秒的价格，历史执行路径里通用的媒体默认价格，不算这个模型的报价。聊天模型附带的图片元数据，不会把它切换到图片计费。只有 token 报价时，按 token 展示；全部缺价时，显示未定价。Gemini Image 系列的图片 token 费率，和计费模式分开解释，Omni 和 Deep Research 使用普通的输出价。按张的报价保留明确的零值和实际来源，价格配置不会改写目录的来源。

<a id="model_attributes"></a>
## 模型属性配置

属性配置保存在 `model_attribute_configs`，包括名称、描述、启用状态和有序的规则；分组关联表用 `group_id` 唯一约束，保证每个分组最多关联一份配置，一份配置可以供多个分组使用。规则和关联在同一个事务里保存，名称或分组冲突时整体回滚。属性配置和价格配置相互独立，停用、删除或解除关联后，恢复默认属性。

规则匹配可请求解析结果里最终的上游模型，计费模型不参与。先按明确的模型身份候选查找精确规则，再按配置顺序匹配末尾通配符，只使用第一条命中的规则。覆盖按字段进行：缺失的键继承；布尔 false 和空的模态数组有明确的含义；模态数组整体替换；管理员填写的长度需要是正整数。未知的字段不会被当成"不支持"或"零容量"。

模型广场先解析可见分组的可请求模型，再用一次数据库查询读取这些分组关联的启用属性档案。共享档案的规则解码一次，结果在本次请求内供各分组使用。控制台的可见分组按分组读取配置。每次展示查询都读取已提交的数据库值，配置写入后发送分组认证的失效通知。属性由展示查询单独读取。分组 DTO 的 `model_attributes` 按公开的模型 ID 索引，市场模型的 `attributes` 和兼容的模态字段来自同一个解析结果。批量属性读取失败时，市场返回模型和价格，属性保持未知。有多条路线时，展示共同的能力和已知的最小上限，`route_differences` 标明路线之间的差异。API Key 别名的导出使用一跳目标的属性，名称和协议资格由可请求目录决定。

管理员接口在 `/api/v1/admin/model-attributes`：`/configs` 提供分页列表和创建，`/configs/:id` 提供查询、完整更新和删除；`/defaults` 支持按搜索词、厂商、能力筛选和分页，`/defaults/model` 查询单个模型的属性，`/defaults/models` 返回候选名称。`POST /defaults/update` 和价格页调用同一个更新器。默认页不叠加分组的配置，未定价模型的属性也可以查询。

属性配置编辑器里，添加模型标签、而当前规则还没填属性时，通过单模型接口填入已知的属性；批量添加时查询第一个新增的模型，通配符不触发填充。明确的 false 和空模态数组原样保留，已有的属性不会被覆盖。查询期间修改了模型或属性、移除了规则或关闭了编辑器，旧的查询结果不会再写进表单；未知模型和查询失败时，保留手动填写的方式。

属性只用于展示和配置导出，和 HTTP、WebSocket、实时会话或媒体任务的准入、参数处理、提供商筛选和故障转移都无关。较小的输出上限，或者明确不支持某项能力，都不会让网关新增拒绝、删除参数、截断或注入请求参数。现有的分组策略、提供商能力和协议兼容行为各自独立执行。

OpenCode 的导出包括显示名、附件、推理、温度、工具调用、模态和长度。它的 schema 要求 `limit.context` 和 `limit.output` 同时存在，所以缺少任何一项时，省略整个 `limit`；它不支持的 `structured_output` 和路线差异字段不会写入。Grok 的导出可以使用有效的显示名，其他客户端保持各自现有的配置格式，不加未知的键。

<a id="group_availability_probe"></a>
## 容量与可用性

市场接口默认附加分组的 capacity 和历史 availability summary。`GET /api/v1/marketplace/models` 接受布尔参数 `include_capacity`，默认值为 `true`。模型广场页面传入 `false`，服务端跳过容量聚合并省略 `capacity` 字段；非法布尔值返回 HTTP 400，reason 为 `INVALID_INCLUDE_CAPACITY`。容量来自当前的提供商和并发数据，历史可用性按开启了 probe 的分组查询，查询范围限于有可请求模型的公开分组。管理员的分组管理继续展示容量，用户侧的模型广场和 API Key 分组选择器展示各自需要的分组信息。容量或可用性读取失败时，模型和价格照常返回，缺失的观测按未知处理。

可用性的窗口和 bucket 粒度来自运行设置，有天数、分钟数和最大 bucket 数的限制，防止公开接口返回过大的序列。时间桶使用配置的时区；它不参与实时调度和计费。

每个分组的 `availability_probe_config` 还控制探测模型、提示词、间隔、单次尝试的超时、User-Agent 和最大重试次数。`max_retries` 表示第一次失败后还可以追加的尝试次数：旧配置没有这个键时默认 3，设为 0 时只执行第一次探测，允许的范围是 0 到 10。每次尝试有独立的超时；第一次或任何一次重试成功后，这一轮的观测记为成功，并停止尝试。一个调度周期只保存一个最终结果，中间的失败不单独计入可用率样本。

探测模型填写分组允许的请求模型名。选择器用这个名称做分组白名单校验，并返回提供商 ID 和分组映射后的模型；测试服务再应用提供商映射。两个映射阶段各执行一次，探测历史记录配置里的请求模型名，便于和管理端的选项对应。

探测轮次、重试和最终结果的编排由 `routing` 负责，租约、原子保存和历史时间桶的查询在 `routing/postgres`；`routing/provider` 提供 cron 日历调度和平台目录数据。app 注入实例标识、时区和执行接口，提供商选择由 `gateway/provider/selection` 提供，探测执行复用 `provider.TestService`，通过 app 构造的 Probe 适配连接。构造时不启动；重复调用 Start 或 Stop 不会注册新任务；停止时，取消维护、领取和请求的预算，并在生命周期的后台总预算内等待在途操作。超时时返回失败，不算排空完成；还没保存的领取，按 PostgreSQL 租约到期的规则恢复。

每个实例的 runner 不允许分钟级的 cron 轮次重叠；单轮领取的到期分组不超过实例的 worker 数，每个领取到的分组都能立即执行，PostgreSQL 租约防止其他实例重复领取。维护、领取和每个分组的探测，分别有独立的超时预算，慢的维护不会挤占合法的重试时间。管理分组 API 里不合法的 `availability_probe_config`，统一返回 HTTP `400`，reason 是 `INVALID_AVAILABILITY_PROBE_CONFIG`。

永久性的模型可用性诊断由 `routing.ModelAvailability` 执行，通过单独的持久候选查询，区分"模型不存在"和"暂时容量不足"。所有入口都按明确的组内关联查询候选，Antigravity 提供商也不会扩大成员范围；查询失败或无法诊断时，交给 503 分支处理，暂时的限流不会被误报为 404。

## 一致性要求

- 市场预取可调度的提供商后，按提供商的全局优先级和提供商 ID 恢复稳定的候选顺序；ProviderGroup 只记录成员关系，没有组内优先级。预取失败时才逐个分组回退；混用两批不同时间点的数据，不能当作原子快照。
- 提供商、分组、价格配置、模型映射或价格更新时，让对应的解析缓存和市场查询缓存失效。
- 上下文区间的上下限，输入、输出和缓存的单价，与实际扣费使用同一个定价解析结果；实际提供商的平台不会成为额外的用户价格键，上游计费模型仍按明确的映射来源确定。
- 市场上"可见"只说明当前有产品、提供商和模型的数据，不保证下一次上游请求一定成功；实际请求仍然要经过限流、并发、凭据和策略的筛选。
- 新平台需要同时提供默认的展示信息、可请求解析、未知价格的处理和平台文档，只把常量加进下拉列表是不够的。
