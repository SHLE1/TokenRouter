# 路由与结算

本文描述 API Key、分组、价格配置、上游提供商、模型映射、价格和用量结算之间的领域关系。它用于修改请求可路由性或扣费时保持共同不变量，不替代具体供应商协议、端点清单或运营定价手册。

## 资源关系

| 资源 | 领域职责 | 主要关系 |
| --- | --- | --- |
| API Key | 客户端凭据和消费边界 | 归属付款用户，可选归属团队；普通 Key 指向一个分组，复合 Key 通过前缀映射到多个分组；可选择自动、指定订阅或仅余额的结算来源 |
| Group | 面向用户的产品/策略边界 | 定义公开/独占状态、倍率、客户端协议、显式回退、模型规则、RPM 和展示策略；提供商可跨平台关联 |
| PricingConfig | 多个分组共享的价格配置 | 一个分组最多关联一个配置；按模型、计费方式、区间与计费来源解析价格，不包含平台维度 |
| Provider | 可实际调用上游的凭据和运行资源 | 通过多对多关系加入分组；保存平台、凭据、代理、并发、优先级、资格、配额和提供商级模型配置 |
| Usage billing record | 一次不可重复应用的资金/额度变更 | 以 `request_id + api_key_id` 认领，绑定付款用户、行为用户、团队、Key、分组和提供商 |
| Usage Log | 已完成请求的可查询事实 | 保存端点、模型链、token/媒体、金额和归属；用于统计与审计，不单独充当扣费账本 |

分组配置、显式回退、管理与复制用例由 `internal/routing` 拥有，SQL/Ent 实现在 `routing/postgres`。价格配置管理、价卡读取与价格缓存也在 routing；模型映射、白名单和功能由独立的分组策略拥有；app 将同一个存储和缓存实例提供给 Key、身份管理与 billing。分组值直接使用 `routing.Group`，管理调用进入所属用例。分组管理直接读取 ProviderStore/KeyStore；容量查询使用提供商存储的批量或逐组只读投影，保留预取失败回退、空结果和逐行阈值取时点。

分组与价格配置的 CRUD、分组复制和排序 HTTP 在 `routing/httpapi`，普通/管理员 DTO 在其 `dto` 子包；分组用量、容量、关联 Key 和倍率/RPM 端点由 HTTP 处理器组合窄接口；倍率配置由 billing 执行，Key 列表由 apikey 提供，用量和 Live 平台检查通过 app 绑定的读取投影。

分组创建/更新涉及的排序锁和提供商关系复制/替换保留原事务边界；提供商关联写入由 `provider/postgres` 的同连接参与方法承担，用户授权清理由 `identity/postgres` 参与。调度 outbox 编码、同连接写入与消费归 `scheduler` 及其 Adapter；同事务 outbox 和提交后尽力发布保持各入口原边界。价格配置缓存发布时取得独立副本，返回的嵌套 JSON 配置也与缓存隔离；管理输入或调用方修改副本不会改变其他请求的规则。

分组是客户端选择的产品边界，价格配置是后台共享的价格边界，提供商是调度执行边界。三者不能合并成一个“供应商配置”：同一分组可以聚合不同平台提供商，不同分组可以有不同产品策略；多个分组可以共享一张价表，并保留各自的基础倍率；提供商又可以加入多个分组并在每次请求时接受独立资格检查。

普通 Key 的 `user_id` 是付款用户。团队 Key 同时携带 `team_id` 和创建/行为成员信息，结算命令中的 `UserID` 与 `ActorUserID` 必须分别表达付款 owner 与实际调用者。Key 自身还拥有状态、过期、总配额、滚动金额限额、IP 规则和模型重定向，不能只把它当作查找分组的随机字符串。

### API Key 结算来源

`api_keys.billing_mode` 与可空的 `preferred_subscription_id` 决定资金来源。历史 Key 和迁移默认值均为 `auto`，保持原有行为。

| 模式 | 运行时选择 | 额度不足或失效时的行为 |
| --- | --- | --- |
| `auto` | 当前分组可消费的订阅优先，之后使用付款主体余额 | 保留订阅与余额混合分配及余额兜底 |
| `subscription` | 请求准入只使用 `preferred_subscription_id` 所指的付款主体订阅 | 订阅不存在、到期、暂停、套餐不覆盖最终分组或预检时额度已耗尽则拒绝；已放行的普通请求若最终费用跨过剩余额度，订阅扣到上限，溢出部分扣付款主体余额并允许形成欠费，不得使用其它订阅 |
| `balance` | 只使用付款主体余额 | 跳过所有订阅解析与分配；不得因持有套餐改用订阅额度 |

创建或修改为 `subscription` 时，服务必须校验订阅属于实际付款主体且当前有效。个人 Key 使用本人订阅；团队 Key 使用 Team Owner 的订阅，成员自己的订阅不能被团队 Key 选择。套餐没有配置分组时表示不限制分组；配置了分组时，指定订阅 Key 的普通分组或复合映射只能取“原有用户权限与套餐分组”的交集。不可用分组回退、复合 Key 最终选组和 handler 的特殊回退都必须再次验证这一交集，不能仅依赖配置页面的过滤。

## 路由决策

路由从客户端模型到上游模型依次经过：复合 Key 选组、Key 级一跳重定向、分组映射、分组限制和提供商级映射。每层要保留输入与输出，形成 `requested_model`、`group_mapped_model`、`upstream_model` 及去重映射链，供权限、计价、日志和响应元数据使用。

请求依次完成选组、分组权限与客户端协议检查、模型映射、组内提供商资格过滤、调度、按选中提供商转换并执行、结算。HTTP 路由不再根据分组平台提前固定处理器。

选定分组后，候选提供商至少满足：

- 提供商属于该分组；专用入口声明强制平台时还须匹配该平台，并处于可调度状态且未过期。
- 分组策略和提供商允许当前模型、端点与认证类型；需要时通过模型映射得到最终路由键。
- 提供商具备特定能力或上游资格，例如图片、视频、Realtime、隐私设置、付费媒体或站点能力。
- 未被当前 failover 排除，未处于临时不可调度窗口，配额和限流状态允许继续尝试。
- 并发槽、等待队列、优先级/负载和会话粘性共同允许本次选择。

普通 Key 必须明确绑定分组；历史未绑定 Key 保留凭据，但新调用会要求先选组。没有自动默认组，也没有允许无分组调度的旁路。提供商可以暂不分组，此时不参加分组调度。

分组可配置客户端限制、无效请求和不可用时的回退目标。Key 的 `fallback_when_group_unavailable` 只允许使用管理员明确配置的不可用回退组；未配置目标就终止。每次换组都重新检查用户、团队、复合 Key、订阅范围、模型和协议权限，并检测回退循环。分组回退可以跨平台提供商集合，不能继承原组未经复核的授权结果。

提供商白名单缺失或为空时使用该平台及认证类型的默认目录，显式映射可增加自定义请求名。非空白名单界定最终模型范围，支持末尾通配符和显式 `*`；范围扩展仍受原生协议、端点、认证和媒体资格约束。模型名前缀不决定提供商平台，协议透传开关也不代表支持所有模型。

OpenAI 兼容 Messages 在尚未向客户端提交响应时，会把管理员临时不可调度规则命中的提供商错误提升为 failover，即使上游状态码本身通常不触发切号；命中模型范围的提供商先写入模型级临时排除，再选择下一提供商。请求内容或 Grok 内容策略导致的拒绝不进入这条通用提供商错误路径。

分组通过 `openai_fast_policy` 选择跟随请求、强制 Fast、强制 Ultra Fast 或关闭两类加速。全局规则保持最高优先级，组级关闭禁止 Key 重新开启，组级强制开启仍允许 Key 关闭。详细优先级与旧布尔字段兼容见 [Fast 与 Ultra Fast 策略](../interfaces/openai_upstream.md#openai_fast_policy)。

关联的价格配置还可启用 `free_openai_fast`。当最终使用的是 OpenAI 提供商且计费档位为 `priority`/`fast` 时，网关保持发往上游的 Fast 档位不变，只用同一分组、价格配置、长上下文和峰值规则重新计算 Standard 用户价格。Usage Log 的 `total_cost`、提供商统计和提供商额度继续保留 Fast 成本；`actual_cost`、余额/订阅分配和 API Key 配额使用 Standard 价格。缺少 Standard 定价时沿用既有缺价零成本记录路径，不把请求改写成普通上游请求；其它平台、普通档位和不可信认证上下文必须忽略该字段。

分组还可设置 `max_reasoning_effort` 与 `max_reasoning_effort_over_limit`。策略只处理客户端显式提供的 `reasoning.effort`、`reasoning_effort` 或 Messages 的 `output_config.effort`；缺省 effort 不会被桥接器补出的默认值误判为客户端请求。先按分组的模型范围映射（精确、前缀或后缀）得到有效档位，再比较 `minimal < low < medium < high < xhigh < max`：`downgrade`（默认）改写为上限，`deny` 返回本地 403 权限错误并标记为业务限制。

推理档位改写仅能来自管理员配置的映射或上限策略，普通转发层不得再隐式改写；`none` 可作为映射和请求审计值，但不参与上限排序。Usage Log 同时保留策略前的请求档位与最终转发档位。复合 Key 在鉴权阶段选出具体分组，之后使用该分组策略。HTTP Responses/Chat、Messages 转换和 Responses WebSocket 的每个请求帧都必须执行同一裁决，且策略快照随 API Key 认证缓存传播。

推理映射与上限按分组保存，实际执行时依据选中提供商、目标协议和模型能力应用。Anthropic 原生档位与 OpenAI 档位的支持范围仍由各执行器校验；混合分组不能让提供商接受原本不支持的值。兼容桥保留 `xhigh` 与 `max` 的区别，避免转换过程改变最终计费档位。

网关在 `requeststate.ExecutionHints` 保留本次规范健康模型，`gateway/provider` 将原始/规范模型、thinking 与端点固化为提供商观测输入。调用后的提供商副本回写仍只覆盖该入口原先拥有的字段，不能把观测快照当成完整提供商更新。

用户/分组 RPM 准入、提供商软计数及三区规则归 scheduler，仍在资金检查后执行，沿用既有故障放行规则。五小时费用窗口规则、批量查询和回填归 billing，usage 聚合仍通过只读端口读取；费用与消费字段不进入调度写权限。

## 可用性与缓存

认证、分组、价格配置和提供商热路径使用缓存或调度快照降低数据库压力，但数据库配置和实时调度状态仍是权威来源。以下变更必须主动失效对应缓存或发布新快照：Key 状态/限额/映射变化，团队关系变化，分组协议/能力/倍率变化，价格配置成员/价格变化，分组路由策略变化，以及提供商状态、分组关系、凭据、代理、并发或资格变化。

价格配置缓存按分组关联、配置与模型规则查找价格，不读取分组或提供商平台。模型映射、白名单和协议策略由分组快照独立保存。价格配置成员或价卡变化失效价格缓存；分组策略和提供商关系变化失效相应认证、模型目录与调度快照。提交失败不能发布一份数据库中尚不存在的新规则。

“可认证”“可消费”和“可调度”是不同状态：

- Key 可认证表示凭据、用户、团队、IP 与资源归属有效。
- Key 可消费还要求余额、订阅、Key 配额和滚动限额允许。
- 分组可路由要求产品策略允许该请求，并存在满足模型与协议要求的组内提供商。
- 提供商可调度还取决于瞬时并发、上游限流、配额、临时封禁和 endpoint 能力。

模型列表只能展示当前身份理论上可请求的模型集合，不能把瞬时没有空闲并发误报成永久无模型；真正请求仍要在调度时重新确认实时状态。

## 价格口径

<a id="group_model_pricing"></a>
### 共享模型价卡与计费设置

价卡及金额算法的唯一实现位于 `billing/pricing`。app 构造 Calculator 与 PriceResolver，通过价格配置端口按分组关联读取有效价卡和计费设置。分组只保留基础倍率 `rate_multiplier`，不再保存模型覆盖价、高峰、长上下文、免费 Fast、批量图片折扣或搜索语音单价。

价格按共享价格配置、统一模型目录价格的顺序解析。配置级设置不依赖模型价卡命中；只有计费设置、没有模型条目的配置同样生效。没有关联配置，或配置停用、删除时，使用统一默认设置和目录定价。价卡支持 token、按次、图片、视频、上下文区间及分时倍率。

显式单价（包括零价）覆盖基础价格；区间未填写的价格桶、区间倍率以及未命中区间的请求使用价卡默认单价，默认价未填写的桶再继承内置单价。只设置 Fast/Flex、Max 推理或分时倍率的条目保留内置价格桶、来源和计费模式，不能给缺价模型创造免费基础价。上下文区间只有倍率且没有可继承基础价时，仍返回 `ErrModelPricingUnavailable`。

价格配置统一保存高峰窗口和倍率、`long_context_pricing_enabled`、`free_openai_fast`、批量图片折扣与预扣倍率，以及搜索和语音可空单价。默认开启内置长上下文，关闭高峰与免费 Fast，批量折扣为 0.5、预扣为 0.6；可空价格读取目录版本中的 `_billing_defaults`，显式零价表示免费。设置和价卡均通过配置缓存读取并复制，修改返回值不会污染后续请求。

提供商统计价卡和用户分组倍率由 billing 拥有。提供商 `rate_multiplier` 只影响提供商成本统计和额度累计，不改变用户扣款。免费 Fast 仅让实际使用 OpenAI Fast 档位的用户按 Standard 基础金额分配资金，Usage Log 的 `total_cost` 与提供商成本仍保留 Fast 金额。Qoder 与其它平台使用相同的价格回退规则。

`PricingAt` 为零继续禁用价格配置分时；目录声明的分时规则所需时刻独立投影，不借此启用配置分时。时区加载由 provider 完成，纯计算只接受显式 Location。网关在结算开始时读取配置级设置，认证快照不再保存旧分组价格字段。

资金分配始终分别携带订阅与余额倍率，不能把首个订阅的 `ActualCost / TotalCost` 同时用作余额按量倍率。确认最终计费模式后，只有 token 模式给这两类倍率及套餐倍率叠加高峰因子；图片、视频和按次模式的高峰因子固定为 1。订阅不足时，溢出部分按余额侧倍率结算。

统一结算根据价卡明确声明的计费模式分派，不从模型名称推断图片计费。`image` 模式按尺寸统一查价；`per_request` 保留先匹配传入标签、再匹配总输入上下文区间、最后使用默认按次价的顺序，即使模型名包含 `image` 也不改变这一规则。

图片和视频不再使用分组级独立单价或独立倍率。普通网关统一按价格配置价卡、目录默认价解析；图片模式乘实际张数，视频模式乘输出总秒数，显式按次价卡乘输出数量，token 价卡按实际用量计费。创作台和批量图片仍按张预占、结算，图片/按次价卡提供单张价格，仅有 token 价卡时查询同一型号的目录按张价，不能直接使用每 token 单价；已提交任务按原定价与资金快照完成结算。

Kimi、Zhipu、DeepSeek 提供商的计费候选不能因为兼容协议而按客户端 Claude 名称借用其他型号价格，因为兼容 Anthropic 请求不代表实际提供 Claude 模型。只有价格配置对该候选配置了显式价格时才保留；提供商/分组映射后的真实 CN 模型仍按正常优先级解析。候选全部被过滤或没有任何非空模型时返回 `ErrModelPricingUnavailable`，沿用零成本告警并保留 Usage Log 的既有路径，不得静默按 Claude 价收费，也不得因定价未知丢弃整条使用记录。

长上下文是模型或价格配置的公开价格策略，不是提供商能力。价格配置存在有效 token 区间时，按总输入量命中显式区间，并禁止再叠加模型内置长上下文倍率；价格配置区间是管理员明确配置的价格合同，不受内置长上下文开关影响。没有有效显式区间时，价格配置 `long_context_pricing_enabled` 决定是否使用模型定价中的阈值和输入/输出倍率；新增设置默认开启，显式关闭只去掉内置阶梯。价格配置的 token 价卡可直接配置自定义区间；`long_context_pricing_enabled` 只控制模型默认阶梯，不控制显式区间。

总输入量包含输入、缓存创建和缓存读取；各模型按自身边界语义判断是否进入长上下文档，进入后整次会话的输入侧与输出侧分别应用对应倍率。模型目录中的 `input/output_cost_per_token_above_*k_tokens` 会在加载时折算为阈值与倍率；条目显式提供任一 `long_context_*` 字段（包括 `0`）时以显式值为准。本地补充可以新增有明确依据的价格及缺失维度，但不能覆盖目录已有字段。用户售价在分组关联的价格配置中设置，覆盖文件不再参与定价；非法补充字段或非对象条目拒绝整次目录更新。

模型广场公开的上下文区间价格必须与相同分组倍率下的 `ActualCost` 一致，在计费模型、服务层级、最终 effort、用量、时刻和倍率相同时，普通提供商和 Spark 影子提供商使用同一价格解析结果。提供商 `extra` 中已废弃的 OpenAI 开关不参与判断；`long_context_billing_applied` 只在该规则实际增加费用时记录为真。

提供商成本基数优先使用 Usage Log 的 `provider_stats_cost`，仅在该字段为 `nil` 时回退 `total_cost`；显式 `0` 表示提供商成本为零。提供商统计和提供商 `quota_used` 都把这个基数乘以提供商 `rate_multiplier`，从而保持同一成本口径。用户余额、订阅和 API Key 配额始终使用 `ActualCost`，不受提供商成本覆盖影响。提供商成本回退到模型文件定价时，必须使用 Usage Log 最终记录的服务层级，并与模型长上下文倍率组合计算；自定义提供商统计价格是最终成本基数，不得再次叠加服务层级倍率。提供商统计不再提供复用用户自定义价的开关：先匹配独立提供商成本规则，再尝试网关默认模型价；缺价时保留日志层既有的 nil 回退语义。

所有共享价和提供商成本价卡使用统一模型空间。同一价表内不能为同名模型保留按平台区分的重叠规则；实际不同的模型应使用不同公开模型 ID。不同提供商成本规则继续按自己的分组、提供商匹配条件和排序独立保存，不跨规则合并。旧价卡迁移中可直接比较的单价逐项取最大，模式、区间、倍率或继承关系不能比较时必须先处理冲突，详见[部署与数据库迁移](../operations/deployment_and_migrations.md)。

共享价格配置仅声明计费规则。分组白名单及其检查阶段见[分组模型与功能策略](gateway_policy_controls.md#group_routing_policy)。

价格配置模型定价显式声明计费模式和计费模型来源：

| 维度 | 可选语义 |
| --- | --- |
| 计费模型来源 | 客户端请求模型、分组映射模型或最终上游模型 |
| 计费模式 | token、按次、图片、视频等，由对应价格字段和区间验证约束 |
| token 桶 | 输入、输出、缓存创建、缓存读取及适用的图片输出 token |
| 倍率 | 系统默认、分组、用户覆盖、订阅计划分组倍率及高峰因子 |

计费来源为上游模型时，要在提供商选定并完成最终映射后才能确定价格；模型白名单按分组配置的独立检查阶段执行，计费模型来源的变化不改变权限。高峰倍率按请求结算时刻和配置时区计算，只叠加到适用的 token 价格；图片按张与视频按秒采用普通分组、用户或订阅有效倍率，不叠加 token 专用高峰因子。所有价格和倍率必须拒绝负值，并在配置写入时校验所选模式所需字段。定价模式冲突检测必须复用定价缓存键的归一化：仅忽略大小写和首尾空白，保留点号、短横线、日期及档位后缀；不同完整 ID 可以配置独立价格，前后端校验与缓存键保持一致。

分组和价格配置模型定价可为 token 模式配置 `time_pricing`：使用 IANA 时区和每日重复的左闭右开 `HH:mm`/`HH:mm:ss` 区间，倍率必须有限、至少 `0.01` 且最多两位小数，区间不得重叠；结束时间 `00:00` 表示当天 24:00，跨午夜区间必须拆成两段。该倍率只作用于 token 的输入、图片输入、输出和缓存价格桶，不作用于按次、图片或视频模式，也不复制到提供商统计规则。纯倍率分组条目未设置分时规则时继承价格配置规则，设置后整体替换价格配置规则（规则时段之外为 1x），不与价格配置分时重复相乘；分组高峰倍率仍独立叠加。

管理员写入时由后端最终校验，价格配置存储在 `pricing_config_model_pricing.time_pricing` JSONB，分组存储在现有 `groups.model_pricing` JSONB 条目中；当前 fork 的迁移文件为 `249_channel_model_time_pricing.sql`。普通请求使用结算时刻，OpenAI WebSocket 使用对应 turn 开始时刻；配置损坏或无法加载时安全回退到 `1x`，不改变既有计费。

Token 计费还支持独立的 `max_reasoning_effort_multiplier`。仅最终转发档位为 `max` 时生效；目录、分组和价格配置可用有限正数声明（`1` 表示不加价），没有明确值时不因型号产生倍率。该规则作用于全部 token 成本桶，并与当前价格、服务层级、区间及分时倍率组合；按次、图片/视频按次和搜索附加费用不乘此倍率。原始请求为 `max` 但策略降档后，按最终档位结算。提供商统计使用模型文件默认价时同样应用最终档位；自定义统计价保持独立最终成本，不重复叠加用户侧倍率。

价格配置字段通过 `268_channel_max_reasoning_effort_multiplier.sql` 持久化，提供商统计规则不接受此字段。

缓存写入可选地拆成 `cache_write_price`（5 分钟）和 `cache_write_1h_price`（1 小时）两档；1h 列为 NULL 时继续把旧列用于两档，保证历史价格配置和提供商统计规则的结算不变。该字段同时适用于价格配置默认价、token 区间和提供商统计价，显式 0 仍表示免费；分档用量缺失时按旧聚合 token 数回退。数据库迁移为 `261_channel_cache_write_1h_pricing.sql`。

Grok 媒体、搜索和 Voice 使用独立计价维度。视频按输出秒计价，价格配置模型价卡的 `video` 模式按 480p/720p/1080p 分档，未配置价卡时读取完整型号和分辨率的目录单价；异步创建不扣费，首次完成观察才用任务级稳定 request ID 结算。搜索以 `search_price_per_1k` 按调用次数附加在 token 费用之上；独立 `/web_search` 和 `/x_search` 的纯工具请求也可单独结算。Realtime、TTS、STT 分别使用每分钟、每百万字符、每小时价格；Realtime 握手或纯文本会话不出账，只有任一方向观察到非空音频负载后才按该连接的会话时长结算。

模型和操作价格缺失继续走既有缺价记录流程，不新增请求前拦截。显式零价与缺失字段分开保存；操作默认价缺失会报告 `operation pricing unavailable`。发布包只补充已核实的 OpenAI Web Search、xAI TTS 与 REST STT 单价；混合搜索计数和通用 Realtime 时长无法完整表达当前供应商收费维度，不配置统一默认金额，管理员仍可显式定价。

所有平台的未知型号均按缺价处理，不按系列或运行时默认模型借价。DeepSeek 与其他型号共用目录，不再通过代码改写费率或自动附加峰谷倍率。结算只查询配置选定的计费模型；该模型缺价时，不继续尝试模型链中的另一型号。媒体独立价卡、显式零价及既有缺价记录流程保持各自语义。

## 用量结算

`gateway/completion.Recorder` 负责供应商用量归一化、模型与请求 ID 选择和 Usage Log 构造；资金预检、查价、分配和提交后资金处理由 billing 承担。`Eligibility.Check` 只处理资金准入，`gateway/admission.FundingAdmission` 固定其与 scheduler RPM 的执行顺序：资金通过后才累计 RPM；Qoder 等待后仅复查资金。

用户日/周/月平台额度已移除，不再授予、预检、结算累加或后台刷新。余额、订阅、团队、Key 限额和提供商上游额度继续各自生效。

身份、Key、推广和完成处理共用同一计费缓存实例。结算经 `Funds.Settle` 进入 billing/postgres 的闭合事务，不能因 context 中已有 Ent Tx 就自动参加外层事务。

billing 从锁定的订阅快照生成有序分配与窗口更新，PostgreSQL Adapter 负责锁序、SQL 更新、outbox 和提交。外层身份/权益事务通过明确的 Ent Tx 参与入口复用连接；参与方法不提交、回滚或发布缓存/通知。

标准结算流程为：

1. 要求非空 `request_id`，规范化 `UsageBillingCommand`，并根据归属、用量、价格和可选请求 payload 摘要生成指纹。
2. 在 PostgreSQL 事务中插入 `(request_id, api_key_id)` 去重记录；已有相同指纹表示请求已应用，已有不同指纹则返回冲突而不是再次扣费。
3. 先以 `FOR NO KEY UPDATE` 锁定付款用户，之后按稳定顺序读取并锁定可用订阅，避免同一用户并发消费穿透限额。
4. 按 Key 的结算模式分配资金：`auto` 先分配适用订阅后扣余额，`subscription` 只锁定并分配指定订阅到额度上限，已放行普通请求的溢出部分按余额倍率记为欠费，`balance` 跳过订阅并只扣余额；结果保存订阅与余额各自金额和有效倍率。
5. 在同一事务内累计团队成员周期用量、API Key 总配额和滚动窗口；提供商额度使用 `COALESCE(provider_stats_cost, total_cost) × provider_rate_multiplier`，其中显式零成本不累计额度。
6. 提交成功后返回 `Applied`、新余额、订阅分配和提供商/Key 配额状态；遇到 PostgreSQL 死锁时由外层开启新事务做有界重试。

`users.balance`、API Key 配额和窗口用量使用 `NUMERIC(20,8)`。进入这些 SQL 加减法前，金额必须按 PostgreSQL 一致的 half-away-from-zero 规则统一量化到 8 位；否则同一笔第 9 位处于 half 边界的金额会因余额减法与配额加法方向相反而产生 `1e-8` 对账差异。幂等指纹仍由量化前的原始金额派生，避免升级前后的同一请求重试被误判为冲突；10 位精度的订阅与用量事实不应在命令入口被提前降到 8 位。

订阅解析必须同时满足生效时间、状态、周期额度和分组覆盖范围。`auto` 没有适用订阅时才走余额倍率，并允许订阅与余额共同承担；锁定订阅模式在请求准入时不允许回退其它订阅或余额。普通请求已经通过预检并成功完成时，如果最终费用超过指定订阅的剩余额度，事务只把可覆盖部分累计到该订阅，订阅用量保持封顶，溢出基础用量按余额倍率扣减付款主体余额并允许余额为负，防止后置结算失败形成零计费记录。该余额扣减只结算已放行请求及并发在途请求，不会把额度已耗尽的指定订阅 Key 转成按量模式；后续新请求仍按订阅快照拒绝，即使用户余额足够也不回退。

指定订阅不存在、失效或不覆盖最终分组时，整笔结算仍须失败，不能伪装成余额扣费。结算命令和幂等指纹都携带模式及指定订阅 ID，避免异步记录阶段因 Key 配置后来变化而选择错误资金来源。团队请求锁定和扣减的是 owner 对应付款用户，但团队成员累计使用 `ActorUserID`，避免账务与行为归属混淆。

批量图片与创作台直接调用唯一 `Funds.Reserve/Capture/Release`，通用任务引用显式包含 scope、任务 ID 和原预占动作 ID。app 注册允许的 scope 与事务参与工厂；`creative/postgres`、`batchimage/postgres` 只用 billing 提供的本次 SQL Tx 写所属任务表的分配与 allowance 标记，billing 不再识别两张任务表。未知 scope 在事务前拒绝；投影失败随资金、去重和额度一起回滚，死锁重试重新创建事务及参与者。

scope 与参与信息不加入历史指纹，v1/v2/v3 快照和原 request ID 保持兼容。任务使用独立的预占/结算命令：提交时持久化余额与订阅分配快照，完成或取消时按同一幂等 request ID 结算、释放差额或回滚适用预记。指定订阅必须在提交上游前完整覆盖预占金额，额度不足就回滚并拒绝，不能复用普通请求“上游完成后再把溢出记为余额欠费”的时序。

## 记录与对账

网关完成计算和提交次序由 `gateway/completion.Recorder` 唯一实现，app 在构造固定执行器前绑定同一 Forward/OpenAI 完成实例。HTTP、SSE、媒体和 WS turn 在提交任务前取得独立主体、资金来源、报文及模型快照；后台不再读取 Gin 或随后变化的请求对象。普通完成、Cyber 失败补记和 Live 零费用记录保留各自原资格，未把一种入口的部分失败扣费扩展到其它入口。

完成输入的同步捕获由 `gateway/provider` 唯一实现，读取原生 Key、身份与提供商记录后复制实际需要的计费字段，不保留凭据或原请求体。请求 ID 前缀优先级、上游自定义 Header、WS 无 HTTP 请求 ID、UTF-8 列宽截断、WS turn 的固定时刻及显式额度更新能力均保持原语义。长上下文算法由模型目录和统一定价决定。

普通结算的 `completion.Store` 由 app 直接绑定唯一 `billing/postgres.SettlementStore`，与任务 `Funds` 共用同一存储。订阅解析仍由该存储在原调用点读取，普通 `Apply` 保持自己的闭合事务，不因请求携带外层事务而自动加入。

完成队列同时等待排队和同步溢出任务，停止后不能重开扩缩容；没有新增持久完成队列。队列或进程超时不表示资金已提交，分析记录也不能替代 billing 的真实幂等/事务结果。

余额和提供商额度阈值由 app 构造的唯一 `billing.BalanceNotifyService` 判断，完成处理直接使用该实例。提供商配置通过 `provider/provider.QuotaNotification` 投影；有事务返回状态时使用该状态中的用量和限额，没有时才按原时机回源。邮件呈现与投递仍由 notification 拥有，通知不参与资金提交。

普通网关在资金事务成功后才尽力写 Usage Log。日志写入失败不能回滚已提交的扣费，也不能因重试日志而再次扣费；反过来，结算失败时不得写一条看似成功的正常使用记录。`usage_billing_dedup` 和实际余额/订阅/配额更新是资金效果的幂等边界，Usage Log 是分析、用户账单展示和运维排查的事实视图。

Usage Log 应保存付款用户、行为用户/团队、Key、提供商、分组、请求 ID、入口/上游 endpoint、实际执行提供商的平台快照、模型链、计费来源、token/媒体明细、基础成本、实际成本和 billing type。管理端用量明细可从列设置启用默认隐藏的请求 ID 列，并直接复制完整值用于跨日志排障；升级旧列偏好时只追加该列的默认隐藏状态，不覆盖管理员已有选择。增加新协议或用量桶时，需同时更新协议解析、成本计算、结算指纹、日志 schema、聚合查询与对账测试。

模型明细与模型分布使用不同但可追溯的展示口径：`requested_model` 保留客户端提交的名称，包括复合 Key 前缀和 Key 级别名；模型分布的请求维度使用完成复合选组和 Key 级重定向后的内部请求模型 `model`。因此用户自定义名称仍可在单条记录和映射链中审计，但不会把相同内部模型拆成多个分布项；上游和映射分布继续分别使用实际上游模型以及“内部请求模型 -> 上游模型”。

## 领域不变量

- 分组定义产品策略，价格配置定义共享定价，提供商定义执行能力；任何一层的 ID 都不能代替另一层。
- 客户端模型、分组映射模型和上游模型必须分别保存，限制、计费和响应恢复使用明确来源。
- 缓存只能加速决定，不能让已禁用的用户、团队、Key、分组或提供商继续工作。
- 资金、订阅、团队成员、Key 和提供商额度效果必须位于同一幂等事务。
- 公开长上下文区间价格必须等于实际用户扣费单价；提供商平台和提供商 extra 不额外改变同一计费口径下的用户价格，价格配置显式区间不能重复叠加模型内置倍率。
- 提供商统计和提供商额度必须使用同一成本基数与提供商倍率；用户资金和 API Key 配额仍只使用 `ActualCost`。
- 指定订阅 Key 的最终路由分组必须被套餐覆盖，预检发现订阅失效或已耗尽时不得放行或静默回退；已放行且成功的普通请求由订阅承担到上限，溢出部分必须形成余额欠费，不能结算为零或把订阅用量扣超。
- `request_id + api_key_id` 相同但指纹不同是冲突，不是可忽略的重复请求。
- Usage Log 不是扣费事务的提交标志；对账必须以去重记录和提供商/权益效果为准。
- 新增计费类型时，要覆盖订阅与余额混合分配、团队归属、重复提交、死锁重试和日志失败测试。
